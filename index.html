        Architecture

        Battleship is a zero-dependency static site — plain HTML, CSS and JavaScript with no build step, so it deploys to any static host (including GitHub Pages) as-is. The code is split into a pure logic core that never touches the DOM and a thin UI layer that renders it. That split is what makes the game testable: the entire ruleset and AI run under Node without a browser.

        Module map

        Data model

        A board is a 10×10 grid of cells plus a ship registry:

        board = {
  cells[r][c] = { ship: <ship index> | null, hit: bool }
  ships[]     = { name, length, horizontal, cells[], hits, sunk }
}

        Every shot goes through fireAt(board, row, col), which returns a small contract both the UI and the AI consume: 

        { result: 'miss' | 'hit' | 'sunk' | 'repeat', ship? }

        The AI opponent

        createAI() is a hunt/target strategy. While hunting it picks from untried cells on a checkerboard parity — every ship of length ≥ 2 covers at least one parity cell, so the fleet is found in at most ~50 probes. After a hit it switches to targeting: the four orthogonal neighbours are queued and tried until the ship sinks. A shot journal guarantees the AI never repeats a cell — a property the test suite asserts across a full 100-shot board.

        Rendering model

        Both boards are rebuilt from state after every change (renderBattle). CSS classes mirror cell state — .ship, .hit, .miss, .sunk-cell — so what you see is always a projection of the model, never a parallel copy of it.

        Bugs & Tests

        The game was verified on two levels: 14 automated logic tests under Node covering rules and AI, and a scripted browser pass that played a complete game in real Chrome — placement through victory through play-again — with a console-error hook installed (zero errors).

        Bugs found and fixed

        1 · Random fleet placement could leave a corrupt, partial fleet

        code review

        placeFleetRandomly() returned false when a ship exhausted its placement retries — but both callers (Random layout, Start battle) ignored the return. A failure would leave a partially-placed board and a game that could never be won.

        Fix: the function now resets the board and retries the whole fleet on failure, and both callers check the return value and show a "try again" message instead of starting on a bad board.

        2 · Shot coordinates didn't match standard notation — and the board had no axis labels

        code review

        Status messages like "Hit at B4!" computed the letter from the row and the number from the column — the reverse of standard Battleship notation. The board also had no row/column labels, so the messages referred to coordinates the player couldn't see.

        Fix: coord() now maps letters to columns and numbers to rows, and labeled axes (A–J across, 1–10 down) were added to all three boards.

        3 · Your shot result disappeared after ~0.5 seconds

        browser testing

        The status bar showed your shot outcome for only ~550 ms before the AI's reply overwrote it — the result of your own turn was easy to miss entirely.

        Fix: the player's result is retained and the AI's reply appended, e.g. "Hit at B4! Enemy fired at G6 — miss." stays until your next shot.

        4 · Placement preview went stale when rotating mid-hover

        browser testing

        The green/red placement preview only repainted on mouseenter. Pressing R while hovering left the old-orientation preview on screen, inviting an invalid placement click.

        Fix: the last hovered cell is tracked and rotating repaints the preview in the new orientation immediately.

        Automated test suite

        test/game.test.js runs 14 assertions with a seeded RNG so every run is reproducible:

        • board shape and empty initial state
        • ship coordinate generation, both orientations
        • out-of-bounds and overlap placement rejection
        • placement mutates the board correctly; illegal placement mutates nothing
        • random full-fleet placement across 20 seeds — always 5 ships, 17 cells, no overlaps
        • fire results: miss / hit / sunk / repeat, including out-of-bounds shots
        • allShipsSunk only when every ship is down; fleetPlaced gating
        • AI sinks a random fleet within 100 shots over 15 seeds, never repeating a cell
        • AI exhausts a full board with no duplicate shot
        • a simulated full game always terminates with exactly one winner

        Verified in the browser (not bugs)

        • Clicks on already-fired cells are ignored — no free AI turn.
        • Clicks during the AI's ~0.5 s turn are dropped — no shot queueing.

        The journey

        How this game went from a one-paragraph brief to a deployed, tested product — every step below actually happened, in this order, during a single Devin session on 2026-10-24.

        1. 1

          The brief

          "Build a Battleship game we can play online against an AI" — plus two extra deliverables: a documented list of bugs found and fixed, and a public GitHub repo with the code.

        2. 2

          Architecture first

          Chose a zero-build static site (deploys to GitHub Pages as-is) and split the code into a pure game.js logic core — no DOM — and a ui.js rendering layer, so the whole ruleset could be unit-tested under Node.

        3. 3

          Core logic

          Board model, placement rules, firing contract, and the hunt/target AI — parity-checkerboard hunting with a neighbour queue after each hit.

        4. 4

          Test suite — green on first run

          Wrote 14 Node tests with seeded randomness: placement rules, firing/sunk detection, AI shot-uniqueness, and full simulated games. All passed immediately — but that only proved the logic core, not the UI.

        5. 5

          Self-review pass — 2 bugs

          Reviewing the UI code surfaced two real bugs before any browser ran the game: shot coordinates used a reversed, unlabeled convention (fixed and added axis labels), and a failed random placement could silently corrupt the board (fixed with whole-fleet retry + caller checks).

        6. 6

          Real browser testing — 2 more bugs

          A scripted agent played an entire game in Chrome, recorded on video: every menu, invalid placements, a 24-shot victory, and a play-again reset. It caught two UX bugs the tests couldn't see — your shot result vanished when the AI replied 0.5 s later, and the placement preview went stale when rotating mid-hover. Both were fixed and re-verified on video.

        7. 7

          Documentation

          Wrote DEBUGGING.md (every bug, root cause, and fix — now the Bugs & Tests tab) and a README covering how to run and how the code is organized.

        8. 8

          Shipped

          Pushed to the public repo rcs-io/battleship and enabled GitHub Pages — you're reading the result.

        9. 9

          Iteration: this site

          The reviewer asked for the game, architecture, test report and journey in one place — so the single page became this four-tab site, re-testing the game tab after restructure.
